## 已修复

**P1 CJK 检索失效** — `src/storage/queries/search.rs`（+ CLI/MCP 两个消费点）

- 现象：`search 订单` 对含「创建订单并扣减库存」的已索引节点返回 0 结果；整串查询却能命中。
- 根因：`nodes_fts` 用 `tokenize='porter unicode61'`，unicode61 把 CJK 表意文字全部归为 alphanumeric，因此无内部标点的整段 CJK 成为**单个 token**；FTS5 只匹配 token 与前缀，不匹配子串。
- 改法：`fts5_search_impl` 改为薄包装——MATCH 主体原样保留为 `fts5_search_match`，返回空且 `empty_reason` 为 None 时进入 `cjk_substring_scan`，仅对含未分词文字的 term 做 LIKE 扫描并 AND 连接，按「标识符命中优先 → 正文最短 → id」确定序排序。
- 理由：不改 schema、不动 INDEX_VERSION、不强制用户重建索引；只在原本已是死路（0 结果）的分支上加一条臂，ASCII 语义完全不变。

**P1 `doctor` 静默撤销一次卸载** — `claude-plugin/scripts/doctor.js`

- 现象：干净 teardown 之后，无参数运行 `doctor`（默认就修，`--check-only` 才只查），
  6 个 hook 条目被写回 `settings.json`，`~/.cache/code-graph/` 连同
  binary-path + install-manifest.json + statusline-registry.json 一并重建，
  **teardown 墓碑被清除**。dev 与非 dev 两种布局均复现。
- 根因：`runRepairs` 的两条写 settings 分支只过 `relicRepairGuard()`，而它问的是
  「这份拷贝是不是活跃安装」，`activeInstallPath()` 为 null 时直接返回 false——正是
  卸载后的状态。两条分支随后都调 `install({clearTombstone:true})`，把唯一能区分
  「刚被拆除」和「装坏了」的标记抹掉。
- 改法：新增同层守卫 `teardownRepairGuard()`，墓碑在场时跳过这两条分支并说明原因 +
  给出撤销命令；谓词可注入，沿用 `relicRepairGuard` 的现有惯例。
- 理由：不动 `install()` 已写明的 clearTombstone 设计，只把「拆除窗口内」这一段挖掉。
  边界由墓碑自身 TTL 兜底——过期后「被拆除」与「装了但没配过」不可区分，后者确实该修。

**P2 `find-binary` 重建被拆除的缓存目录** — `claude-plugin/scripts/find-binary.js`

- 现象：teardown 完成、墓碑在场时，一次 `findBinary()` 就把 `~/.cache/code-graph/`
  连同 `binary-path` 建回来。README 承诺 uninstall「drop the cache」。
- 根因：`writeCacheEntry` 冷路径 `mkdirSync(path.dirname(CACHE_FILE))`，而 CACHE_FILE
  由它自己 `os.homedir()` 拼出、不走 `cache-paths.js`——正是该文件头部 JS-05 注释
  抱怨过的反模式，于是 auto-update 的三道门没覆盖到它。它还是四者中调用最频繁的
  （每次冷解析、每个 hook）。
- 改法：写入前查 `uninstallTombstoneActive()`，与另外三道门同一谓词、同样 fail-open。
- 理由：跳过只损失一次重新探测，不产生错误答案——调用方已经拿到解析结果，这里只是备忘。

## 遗留风险与待办

**P2 tree-sitter `&raw`（需 §5 hard-AUTH，未修）**
借用名为 `raw` 的绑定（`&raw` / `&raw[..]` / `&raw.field`）被 `tree-sitter-rust` 0.23.3 误判为 `&raw const` 指针运算符的开头，整个表达式乃至外层函数从索引中消失。`&mut raw`、`&self.raw`、真正的 `&raw const x` 均正常。
实测（161 个 Rust 文件）：0.23.3 有 8 个文件 29 个 ERROR 节点、提取 3914 项；0.24.2 为 0 个文件 0 个 ERROR、提取 3915 项——**净损失 1 个符号**（`src/cli/commands/affected.rs` 的 `cmd_affected`，被 `main.rs` 调用）。
升级可行性已实测：`tree-sitter-rust` 0.24.2 需要 `tree-sitter` 0.25（0.24.7 下运行时报 `LanguageError { version: 15 }`），而 19 个语法 crate 在 0.25.10 下**全部加载成功**。
成本：prod 依赖 bump（§5 hard-AUTH）+ 19 种语言提取逻辑重新验证 + 很可能 INDEX_VERSION bump 强制全体用户重建。已在 README「Known limitations」中如实记录。

**第三扇门 `launcher-install.js`（同族，已实测，决定不修）**
`installBinaryInBackground` → `acquireLock(INSTALL_LOCK_FILE)` → `mkdirSync(CACHE_DIR)`，
两个文件都没有任何墓碑引用。与上面两处同族，但取舍不同：launcher 的职责就是
「二进制缺失时装一个，否则 MCP server 没引擎」，README 把这条写成即使
`CODE_GRAPH_NO_AUTO_UPDATE=1` 也保留的行为。挡住它 = 让还在运行的 MCP server 拿不到引擎。
find-binary 那处能改是因为它纯粹是备忘优化，跳过零代价；这处不是。

**待观察 — MCP 服务器偶发启动停顿**
早期约 60 次 `serve` 启动中有 2 次 >60s 无响应；此后 ~90 次（含 12 核满载）0 次复现，单独复现每个帧均在 50ms 内正确响应。按「复现不了的不修」标记，不做改动。若再次出现，先查 `.code-graph/index.lock` 持有者。
